# Knot (낫) - 공동 목표 빌드 플랫폼 통합 제품 요구사항 정의서 (PRD)

이 문서는 'KNOT' 프로젝트의 기획적 결정 사항부터 실제 개발에 즉시 착수할 수 있는 화면 구성(Pages), 유저 플로우(User Flow), 데이터베이스 스키마(DB Schema)까지 모두 포함한 최종 기획 명세서입니다.

## 1. 프로젝트 탄생 배경 및 비전
* **배경**: 기존 'DATT(데이트 코스 추천)' 프로젝트에서 겪은 수동 데이터 수집(크롤링)의 한계를 극복하고자, 유저가 스스로 유용한 데이터를 만들어내는(UGC) 구조를 고민함.
* **비전**: 커플, 친구, 동업자 등 **"두 사람이 함께 공동의 목표(결혼, 여행, 프로젝트 등)를 세우고 달성해 나가는 범용 로드맵 플랫폼"**으로 진화함.

## 2. 핵심 제품 철학 (Core Philosophy)
### 2.1. 기여도가 아닌 '원팀(One-Team)' 스코어보드
* **문제**: A가 얼마, B가 얼마를 냈는지 명시적으로 보여주면 비교와 스트레스가 발생함.
* **해결책**: 앱 내부에서는 개별 기여도를 묻거나 저장하지 않음. 오직 **"우리가 함께 모은 총액(또는 카카오 모임통장 잔고)"**만을 거대한 전광판(게이지바) 형태로 덮어쓰며, 함께 목표를 달성하는 성취감에 집중함.

### 2.2. 일상을 담는 유연한 타임라인
* 단순히 굵직한 이벤트(상견례, 집 계약 등)만 기록하는 것이 아님.
* 타임라인 노드에 **'일상적인 데이트 일정'**과 그날의 **'지출 내역'**을 함께 태깅할 수 있도록 하여, 어쩌다 한 번 쓰는 앱이 아닌 '매주 데이트 장부'처럼 쓰이는 높은 활용도를 추구함.

## 3. 핵심 유저 플로우 (User Flow)
1. **가입 및 팀 생성**: 유저 A가 소셜 로그인(카카오/구글)으로 가입 -> '팀 생성' 클릭 -> 6자리 초대 코드 발급
2. **팀 합류**: 유저 B가 가입 -> '초대 코드 입력' -> 유저 A와 유저 B가 하나의 '팀(Team)'으로 묶임
3. **목표 설정**: 두 사람이 첫 번째 공동 목표 생성 (예: "우리의 첫 신혼집 자금 모으기", 타입: 금액, 목표치: 5000만원)
4. **타임라인 기록 (일상 사용)**: 
   - 큰 퀘스트(마일스톤) 추가 (예: "웨딩홀 투어")
   - 일상 데이트 일정 추가 (예: "이번 주말 홍대 데이트")
   - 지출 내역 태깅 (데이트나 퀘스트 완료 후 타임라인 노드에 지출액 기록)
5. **공동 게이지바 업데이트**: 카카오 모임통장 등에 입금할 때마다 앱의 총액(게이지바)을 갱신하며 함께 성취감을 느낌

## 4. DATT 유니버스와의 시너지 (Growth Flywheel)
KNOT은 그 자체로 독립적인 서비스이면서, 동시에 DATT의 부족한 매장 DB를 채워주는 거대한 파이프라인 역할을 함.
### 4.1. 유저 생성 콘텐츠(UGC)를 통한 DATT DB 확장
* **데이터 파이프라인**: 유저가 KNOT 타임라인에 '데이트 일정'이나 '청첩장 모임 식당'을 기록할 때, **"이 멋진 장소를 DATT에 추천(공유)하시겠어요?"**라는 동의(체크박스)를 받음.
* **플라이휠 효과**: 유저가 동의한 양질의 핫플 식당, 웨딩 베뉴 데이터가 자동으로 DATT 생태계로 흘러 들어가 크롤링 없이도 DB가 풍성해짐.

## 5. 구체적인 화면(Page) 명세
### 5.1. `/login` (로그인 및 온보딩 페이지)
- **UI 요소**:
  - DATT 패밀리 계정 연동을 강조하는 소셜 로그인 버튼 (카카오, 구글)
  - 로그인 직후 소속된 팀이 없으면 [새 팀 만들기] / [초대 코드 입력하기] 버튼 노출

### 5.2. `/dashboard` (메인 대시보드 - 목표 한눈에 보기)
- **UI 요소**:
  - **최상단**: 팀 이름과 프로필 (예: "A ❤️ B")
  - **메인 전광판 (One-Team Gauge)**: 
    - 텍스트: "목표 달성까지 2,500,000원 남았어요!"
    - 비주얼: 화면 중앙을 꽉 채우는 원형 프로그레스 바(0~100%)
    - 액션 버튼: `[+ 모임통장 잔고 업데이트]` 버튼 (개별 기여도 입력 없이 총액만 덮어쓰기)

### 5.3. `/timeline` (우리의 기록 타임라인)
- **UI 요소**:
  - 세로로 길게 이어지는 예쁜 타임라인 선과 노드(Node)들
  - **[+ 노드 추가]** 버튼을 누르면 3가지 타입 중 선택 가능:
    1. **마일스톤(퀘스트)**: 굵직한 목표나 할 일
    2. **데이트 일정**: 소소한 만남 기록 (DATT 서비스와 엮을 수 있는 핵심 포인트)
    3. **지출 기록**: 해당 일정/데이트에서 발생한 비용을 적어 타임라인 위에 돈이 나간 흐름을 박제

### 5.4. `/quests` (세부 할 일 목록)
- **UI 요소**:
  - 타임라인 노드 하위에 달리는 세부 체크리스트 (예: 웨딩홀 투어 노드 아래에 A웨딩홀, B웨딩홀 체크박스)
  - 스와이프 액션으로 직관적인 완료 처리

## 6. 구체적인 데이터베이스 스키마 (Supabase)
실제 구축될 PostgreSQL 데이터베이스의 핵심 테이블과 컬럼 구조입니다.
### 6.1. `users`, `teams`, `team_members`
- 통합 계정 및 커플(팀) 연동을 위한 기본 테이블
### 6.2. `goals` (공동 목표)
- `id`, `team_id`, `title`, `goal_type`
- `target_value` (Integer): 목표 수치
- `current_value` (Integer): 현재 달성 수치 (모임통장 총액)
### 6.3. `timeline_events` (타임라인 노드 - 핵심 확장)
- `id` (UUID)
- `team_id` (UUID)
- `event_type` (Enum): `MILESTONE`(큰 퀘스트), `DATE`(데이트 일정), `EXPENSE`(지출)
- `title` (String): 이벤트 이름 (예: "홍대 데이트", "웨딩홀 계약금")
- `amount` (Integer, null 허용): 지출이 발생한 경우 금액 기록
- `event_date` (Date): 일정이 있는 날짜
- `is_completed` (Boolean): 완료 여부

## 7. 프라이버시 및 보안 정책 (Privacy Policy)
### 7.1. 기술적 고립 (Row Level Security)
* 본 서비스는 유저의 가장 내밀한 돈 이야기와 일상 메모가 담김.
* 백엔드 단에서 **RLS(행 수준 보안)**를 적용하여, A팀의 유저는 해킹을 시도해도 B팀의 데이터를 기술적으로 100% 열람할 수 없도록 원천 차단함.
### 7.2. 관리자의 열람 권한 범위
* **열람 불가**: 관리자는 유저의 사적인 타임라인 텍스트나 정확한 공동 자금 액수를 임의로 들여다보지 않는 것을 철칙으로 함.
* **열람 허용**: 
  1. 유저가 DATT 생태계로 전송하기로 '명시적으로 동의(체크)'한 장소 데이터.
  2. 서비스 개선을 위한 익명화된 행동 통계 (예: 앱 접속량, 특정 마일스톤 생성 횟수 등).
